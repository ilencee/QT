## 追加: "Win error 740" — 启动需要管理员权限的软件报错

## 追加: SOC Pro51 仍报权限错误 — 真正的坑是 c_intptr_t

现象: 修完 740 后用户仍报权限错误。诊断 (零副作用 CreateProcessW CREATE_SUSPENDED + ShellExecuteW 实测):
- **SOC Pro51.exe 的 manifest 是 requireAdministrator** (本身要管理员), 而 SOC Programming Tool Enhance.exe 是 asInvoker — 工作助手当前进程非管理员 (IsUserAnAdmin=0) → Popen SOC Pro51 必抛 740
- **真凶**: `_start_via_shell` 里 `ShellExecuteW.restype = ctypes.c_intptr_t` 在 Python 3.9 中**不存在** (`AttributeError: module 'ctypes' has no attribute 'c_intptr_t'`) → 被 `except Exception: return False` 吞掉 → 永远返回 False → 永远弹"无法以管理员权限启动"
- 修复: restype 改 `ctypes.c_ssize_t` (实测 notepad/SOC Pro51 open verb 均返回 42>32 成功, 触发 UAC)

教训: 用 ctypes 时在目标 Python 版本实测类型存在性; 避免 `except Exception: return False` 吞掉编程错误 — 至少把异常原因计入调试。实测 SOC Pro51.exe requireAdministrator → 桌面双击也是靠 UAC 弹窗提权, 用户"桌面能打开"与此一致。

## 追加: 修复 AI 线程闪退 (QThread deleteLater 陷阱)

用户反馈"软件会闪退"。用临时诊断脚本复现, 根因是 **`finished.connect(self.ai_thread.deleteLater)` + Python 引用残留**:
- 线程结束 → deleteLater 排队删除 C++ 对象, 但 `self.ai_thread` 仍指向已删除对象
- 再次点击 (测试连接第2次/再次润色/AI分析) 时 `self.ai_thread.isRunning()` → `RuntimeError: wrapped C/C++ object of type DeepSeekThread has been deleted` → PyQt 事件循环未捕获异常 → **程序闪退**
- closeEvent 里 `thread.isRunning()` 同样崩 (测试进行中关窗口)

修复 (三处统一, settings_page.py / text_polish_page.py / power_conversion_page.py):
- 删除 deleteLater 连接, 改 `finished.connect(self._on_ai_thread_finished)`; 槽内 `self.ai_thread = None` (线程已结束, Python GC 安全回收) + 恢复按钮
- 启动前连点保护改为 `if self.ai_thread is not None: return` (不再查 isRunning, 对象有效即可)
- closeEvent: `requestInterruption()` (无害) + `wait(5000)`; 线程已结束才置 None (run 有 urlopen timeout=60 兜底, 正常网络 5s 内必结束)
- 验证: 诊断脚本 [B] 二次点击、[C] 关窗不崩, 全流程回归 OK, lint 0

## 经验: PyQt QThread 生命周期管理规范

- **禁止** `finished.connect(thread.deleteLater)` 后仍保留 Python 引用 → 访问已删对象必崩
- **正确模式**: finished → 清空引用槽 (置 None) → 线程已停止, GC 安全; closeEvent 里 wait 前先 requestInterruption, 且仅在线程结束时释放引用

## 修复: 打包脚本失效 — bat 编码 GBK 与 chcp 65001 冲突 (UTF-8+CRLF 才是正确形态)

用户反馈"现在无法打包"。排查过程:
1. `python -m PyInstaller` 手动打包**成功** → 核心打包链路没问题, 问题在 bat 脚本本身
2. 跑 build_exe.bat 报 `'open'/'exist'/'-m' is not recognized` + 中文乱码 → **cmd 把 bat 行解析断裂**
3. 根因: git 里 build_exe*.bat 是 **GBK 编码 + LF 换行**, 但脚本第 2 行 `chcp 65001` 切到 UTF-8 代码页 → cmd 用 UTF-8 解码 GBK 中文字节 → 行错乱/变量(set APP_NAME)失效
4. 三种编码实验 (T1 GBK+chcp65001 / T2 UTF-8+chcp65001 / T3 UTF-8BOM+chcp65001): **仅 T1 乱码, T2/T3 完全正常** (中文 echo/set/if/python 全对)

修复:
- 两个 bat 转 **UTF-8 (无 BOM) + CRLF** 写入 (与 chcp 65001 匹配); 验证 cmd 解析正常
- 实测打包: one-dir `Build complete` (dist\工作助手\) + onefile `Build complete` (dist\工作助手_单文件\), 均 0 错误
- 顺带容错: 本机 **Pillow 未安装** (pip 装不上: 清华源 SSL 失败/官方源 ProxyError), build_exe*.bat 第 1 步 `from PIL import Image` 会抛 ModuleNotFoundError → 改为 `2>nul` + `if errorlevel 1`: 已有 app.ico 则警告沿用, 无 ico 才报错退出
- requirements.txt 补 `pillow>=9.0.0`
- 清理测试临时文件; `工作助手.spec` 被测试命令改写过 icon 绝对路径 → git checkout 恢复

**纠正旧结论**: 之前 (6-19 条目) 说"bat 保持 GBK 编码"是误判——真正修复当时的可能是 fix_bat_icon_path.py。**正确形态: bat 必须 UTF-8(无BOM)+CRLF 与 chcp 65001 匹配**; GBK 编码的 bat 千万不要配 chcp 65001。注意 scripts/fix_bat_encoding.py (转 GBK) 会制造本 bug, 勿再使用。
